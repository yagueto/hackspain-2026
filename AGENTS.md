# Backend

- Trabaja en `apps/api` usando su `.venv` (`uv sync`). Verifica con `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy app` y `uv run pytest -q`.
- Para ejecutar también los tests SQL usa `TEST_POSTGRES_DSN` contra PostgreSQL de desarrollo. Cada test crea su propio schema temporal. El servicio de pruebas documentado usa el puerto 55432; Compose de desarrollo usa 55433 y volumen persistente.
- Persistencia: `STORAGE_BACKEND=postgres` y `DATABASE_URL`. Sobre una base **vacía** el arranque aplica el esquema v1 solo; con el esquema a medias o en otra versión falla en alto sin tocar nada (podría ser una base ajena por un DSN equivocado) y hay que revisarlo con `uv run python -m app.store.migrate [--apply]`. No necesita credenciales HappyRobot. Los únicos backends son `memory` y `postgres`; el adaptador Twin se eliminó y toda la lógica SQL vive en `app/store/postgres.py`.
- Configuración: entorno del proceso > `.env.local` > `.env`. Ambos dotenv y `.devin/mcp_config.local.json` deben seguir ignorados. Nunca imprimir ni versionar claves, URL privadas de webhooks o secretos.
- Las pruebas aíslan Settings de ambos dotenv y del entorno, y bloquean el transporte HTTP real. Usar ASGITransport o MockTransport; no desactivar esta protección para hacer pasar un test.
- Nunca activar comunicaciones reales durante verificaciones automáticas. Mantener `HAPPYROBOT_MODE=simulated`, `AGENT_AUTOSTART=false`; vaciar `OPENAI_API_KEY` en el proceso para pruebas completamente locales.
- Los avisos de texto salen por el workflow `send_telegram` (`HAPPYROBOT_WF_TELEGRAM`): el backend no habla con la API de Telegram ni con ningún puente. El canal SMS se eliminó por completo (`ActionKind.sms` y `/control/sms` ya no existen); `apps/simulator/simulator.py` todavía contiene una rama `kind == "sms"` inútil. El aviso queda `dispatched` hasta que llega la observación `message_outcome`; no darlo por entregado antes. Una orden cuyo `workflow` no corresponde a su `kind` debe fallar, nunca cambiar de canal.
- Solo las llamadas mueven `contact.reliability`, porque pondera la selección de medios. Un aviso de texto entregado no es evidencia de que la persona responda.
- `app/domain/movement.py` + `Orchestrator.advance_missions()` acercan las unidades a su destino. Solo avanza lo que está `en_route`, es decir, lo que **aceptó la llamada**: una orden enviada no significa que nadie se haya puesto en marcha. La posición es una estimación por tiempo transcurrido (`travel_from`, `travel_started_at`, `travel_minutes`, `travel_progress`), nunca GPS, y va marcada con `position_estimated`. Un parte de campo `resource_status` con `location` manda sobre ella y reinicia el trayecto desde ahí. Llegar pone `on_scene` pero **no** cierra la misión: eso lo dice un parte, no un cronómetro. Un avance menor del 1 % no se publica, para no versionar el estado en cada ciclo.
- En el dashboard, `DemoRouteSimulation` ya no inventa el movimiento ni descarga rutas: interpola sobre la ruta que trajo el mapa usando la salida y la duración del backend. El mapa es el único que pide rutas; si el consumo del avance filtrase esa lista, cambiaría en plena descarga y la repetiría contra el OSRM público. Las misiones de avisos ciudadanos no tienen ruta a propósito (no se manda una dirección privada al proveedor público), así que su marcador usa la posición estimada del backend.
- En HappyRobot, los POST nuevos usan `webhookSchemaVersion=2` y `body={schemaVersion:2,contentType:"application/json",raw:...}` con tokens `{{$var:group_id.variable_id}}`. Confirmado que la conversión automática de strings falla: `url` y `headers[].value` exigen arrays Plate con nodos `variable`. Los `group_id` por índice (`0`) solo valen al crear en lote; para añadir nodos usar el `persistent_id` real.
- El MCP `happyrobot-workflows` (`.devin/mcp.json`) permite crear y validar workflows. `test_all` comprueba estructura y referencias, pero algunos nodos POST pueden ejecutarse; un nodo "skipped — success" no se ha ejecutado. No publicar versiones ni rellenar variables con secretos sin petición explícita.
- Publicar es **por entorno**: una versión live en `production` no la usan los runs de `development`, y el backend dispara con `HAPPYROBOT_ENVIRONMENT`. Para mover una versión hay que despublicarla antes; si no, `publish` responde "Version is already live". `fork` conserva los `persistent_id`, así que las referencias `{{$var:...}}` siguen valiendo. El aviso de "variable references could not be resolved" sobre params del trigger es un falso positivo: resuelven en ejecución.
- El nodo Webhook POST solo expone `error` como variable de salida, no `status_code` ni `response`. Y un nodo hijo solo se ejecuta si el padre tuvo éxito, así que no se puede ramificar sobre el fallo de un POST.
- No detener la API antigua con almacenamiento memory sin conservar su estado o pedir confirmación. No eliminar volúmenes de PostgreSQL.
- `apps/simulator` puede contener trabajo sin versionar del usuario; no incluirlo en commits ajenos. No hacer push sin petición explícita.
- La recepción ciudadana por Web Call usa `POST /api/v1/webhooks/happyrobot/inbound` con `X-Webhook-Secret`, `run_id`, `timestamp` ISO con zona horaria y el parte estructurado. No requiere una acción saliente. `incoming_calls` se conserva en el snapshot PostgreSQL y se difunde por SSE; cada run tiene un único aviso actualizable y los informes atrasados se ignoran.
- **El agente es autónomo por defecto: decide, localiza, reserva y despacha sin operador.** Solo somete a confirmación humana lo crítico, definido en `AgentConfig`: los avisos con `severity` en `approval_required_severities` (`vital`) y los `TaskKind` de `approval_required_for` (`evacuate_zone`). Lo demás se retiene `hold_seconds` (10 s) para poder anularlo y después sale solo. `app/domain/autonomy.py` es el único sitio donde vive esa frontera; con `autonomous=false` todo vuelve a pasar por una persona. No reintroducir puertas de aprobación en el camino no crítico.
- Una decisión crítica sin confirmar a los `escalate_after_seconds` (30 s) genera **un solo** aviso por `send_telegram` (`escalated_at` lo hace idempotente) y **sigue esperando**: el escalado no despacha. Ese aviso no lleva `task_id` en la acción a propósito, porque el outbox trataría la orden como misión y la cancelaría por "requiere aprobación".
- El usuario eligió Web Call. Los puntos aportados por el informante requieren ambas coordenadas válidas. La geocodificación es automática siempre que falte GPS, sin consentimiento ni gate de demo: en esta demo de hackathon las direcciones del aviso, incluidas las privadas, salen hacia `GEOCODING_ENDPOINT` (por defecto el Nominatim público de OSMF). Fuera de la demo hay que apuntarlo a una instancia propia. No deducir GPS del teléfono. Un resultado geocodificado se etiqueta como aproximado; los candidatos ambiguos o centros de poblaciones nunca se seleccionan solos, y sin ubicación utilizable la propuesta queda **bloqueada** (`blocked_reason`), nunca cancelada ni despachada a un punto inventado.
- `Recepción llamada ciudadana`: `Web call` → `Inbound Voice Agent` → `enviar_incidencia` → POST al backend. Sin chatbot de texto ni llamadas salientes; `require_webcall_auth=true`. `INTAKE_BASE_URL` e `INTAKE_WEBHOOK_SECRET` se configuraron privadamente solo en development; el secreto coincide con `HAPPYROBOT_WEBHOOK_SECRET`. No cambiar secretos ni otras publicaciones sin autorización explícita.
  - v7 `01a0bb20-6572-77be-8ed8-5834ca86568a` (slug `x72w6ey05cu3`) está **publicada y live en development** con autorización del usuario, y sustituye a la v5, que se despublicó para poder moverla. Es un fork de la v5 con el prompt adaptado a la autonomía: no pide permiso de búsqueda, envía `location_public_search_allowed=false` y ya no promete aprobación previa; mantiene la prohibición de anunciar unidades en camino, porque el POST sigue sin devolver esa respuesta. Se verificó releyendo el nodo POST que el fork conservó URL, `X-Webhook-Secret` y las referencias `{{$var:...}}` al `persistent_id` del tool. **No se ejecutó `test_all`**: el nodo POST apunta al backend real y podría ejecutarse de verdad.
  - v5 `01a0ba83-54d9-7d83-8454-b78c35aa7801` queda despublicada como versión anterior; su prompt todavía pide consentimiento para buscar la dirección y promete revisión del operador.
  - El parámetro `location_public_search_allowed` del tool se conserva aposta; borrarlo rompería las referencias del body y cambiar la definición del tool devolvería `tool_call_result_ack` a `unack`, obligando a reabrir el panel a mano.
  - Existe además una v6 `01a0bad1-112b-7700-b5c1-a34b338658bb` en borrador que no creó este trabajo y que no se ha tocado.
- Para publicar un tool nuevo, HappyRobot exige abrir `Tool Call Result` en su interfaz. El MCP puede responder éxito al escribir `configuration.tool_call_result_ack` pero no cambia `unack`; el usuario abrió el panel y pasó realmente a `ack`. Un resultado de previsualización con campos null no prueba un fallo de una conversación: contrastar runs y recibos.
- En la sesión local el frontend 4200 apunta a la API de 8001. Un proxy de callbacks en 8010 expone solo `POST /api/v1/webhooks/happyrobot/inbound` a través de un túnel separado; no expone `/state`. Ese túnel es temporal: si se reinicia cambia la URL y hay que actualizar privadamente la variable de development.
- **La instancia de 8001 corre con `uvicorn --reload` y `HAPPYROBOT_MODE=live`.** Con `storage=memory`, cualquier edición de un `.py` reinicia el proceso y **borra todo el estado**: ya ocurrió una vez por editar `app/agent/executor.py` con la API arriba. No editar backend con una instancia en memoria viva sin avisar. `apps/api/.env.local` (ignorado por Git) ya fija `STORAGE_BACKEND=postgres` y `DATABASE_URL` contra el Compose de 55433, con el esquema v1 aplicado, de modo que tras reiniciar el estado sobrevive a los reload. Un cambio en cualquier dotenv solo surte efecto al reiniciar el proceso: `Settings` se lee al arrancar y está cacheado.
- Las salidas siempre pasan por un workflow de HappyRobot; el backend no marca teléfonos ni habla con la API de Telegram. Pero eso **no** implica que no suene nada: `call_responder` marca el `phone` del contacto, que sale de `SEED_PHONES`. En este `.env` ese valor es `"+34"` (solo prefijo, cero dígitos), así que ninguna llamada puede alcanzar a una persona; si alguien pone ahí un número real, las llamadas autónomas serán reales. Comprobar `SEED_PHONES` y `HAPPYROBOT_MODE` antes de provocar un despacho.
- `HAPPYROBOT_WF_TELEGRAM` se cableó al workflow `Crisis - Aviso Telegram` (`01a0b9ec-2f1d-7881-b454-ddc2fd8b5f4b`, v2 live en `development`) y se eliminó el residuo `HAPPYROBOT_WF_SMS` del canal SMS ya suprimido. Hasta que se reinicie la API, `healthz` seguirá indicando `telegram: false` y los escalados fallarán con "workflow id vacío".
- Cancelar una misión cuya orden ya salió **no** libera la unidad, a propósito: se necesita un parte de campo. Para liberarla, una observación `resource_status` con `status=available` y el `task_id` correcto, que además cierra la tarea como `done`.
- El MCP puede responder éxito a un `update` de `event_id` sin cambiar el tipo real. Releer siempre el nodo. Para reemplazar el trigger, `update_workflow_nodes action=add` con un trigger inicia un árbol nuevo y sustituye el anterior: hacerlo solo en un borrador propio, reconstruir sus hijos y usar los nuevos `persistent_id`. Un agente nuevo crea automáticamente su prompt y la vinculación `call` al trigger Web Call.
- Precaución adicional sobre `test_all`/`fix_broken_vars`: un POST no omitido puede intentar ejecutarse. En el chatbot devolvió `unsupported protocol scheme` con la base vacía. No repetir estas comprobaciones con endpoints reales bajo la suposición de que siempre son puramente estructurales.
- `app/domain/intake.py` decide qué propuesta merece cada aviso; quien la ejecuta es `Orchestrator.reconcile_intake()`, que además cancela las misiones que un aviso corregido invalida. El webhook de entrada la llama, pero **no** geocodifica: eso lo hace `locate_pending_reports()` en el bucle, porque quien llama es el workflow que está atendiendo al ciudadano y no debe esperar a un proveedor externo. Cada propuesta conserva `incoming_call_id`, fecha del aviso y destino. La aprobación de un aviso exige `expected_updated_at` y `confirm_location=true`; una evacuación no, porque no tiene parte cuya ubicación revisar.
- La ventana `hold_until` se comprueba en `_dispatch_pending` **después** de validar la tarea: una orden retenida que el aviso ha invalidado se cancela, no se queda esperando a salir hacia un destino viejo.
- `POST /control/incoming-calls/{run_id}/location` **acepta la corrección aunque haya misión en curso**: corregir el destino es lo que la invalida, no al contrario. Cancela sus órdenes (con `cancel_run` si la llamada ya salió) y vuelve a proponer contra el punto bueno. Obligar a cancelar antes dejaba al agente replanificando hacia la ubicación equivocada mientras el operador teclea la buena. Por eso una propuesta cancelada se reabre mientras no quede ninguna orden nuestra `pending`/`sending`; la unidad ya avisada **no** se declara libre por eso, hace falta un parte de campo. El reintento de geocodificación sí sigue bloqueado con misión en curso: buscar no debe redirigir a nadie por sorpresa.
- `app/integrations/geocoding.py` mantiene la disciplina del proveedor: cola global del runtime, mínimo 1,1 segundos entre inicios, caché acotada y países limitados a España. No hace autocomplete ni polling. Guarda candidatos y errores en `incoming_calls[].resolution`, sin inventar lat/lng ni atribuir GPS. Un error del proveedor no descarta el aviso; un resultado tardío no sobrescribe una corrección.
- Los controles locales de geocodificación, ubicación, cancelación, aprobación y la parada de emergencia exigen `X-API-Key` (`API_KEY` del backend). `POST /control/pause` es la parada: detiene los envíos nuevos, incluidos los retenidos, pero no cancela runs ya enviados ni libera unidades movilizadas; reactivar es explícito y el arranque nunca lo hace solo. `POST /control/resume-simulated` es una acción aparte y rechaza modo live. Las órdenes simuladas no generan automáticamente aceptación del recurso ni significan ayuda movilizada.
- El operador simulado de `apps/simulator` (`operator_loop`, desactivable con `--no-approve`) no puede falsear los casos críticos: aprueba sin `confirm_location` ni `expected_updated_at`, y el backend lo rechaza con 409 para toda tarea con `incoming_call_id`. Solo auto-aprueba evacuaciones.
- Las preguntas del registro viven en `coordination_questions` del snapshot, también en PostgreSQL. `POST /control/questions` y `/control/questions/{id}/answer` requieren la clave de operador. Sus campos JSON internos usan camelCase para compartir contrato con el dashboard. El bucle del servidor resuelve vencimientos sin depender de una pestaña abierta; las respuestas son idempotentes por pregunta y las acciones se revalidan antes de guardarse. La respuesta por vencimiento solo puede mantener la actuación o registrar una nota, nunca aprobar, cancelar o movilizar recursos. `/control/questions/demo` exige escenario demo y salidas simuladas.
- Desactivar la autonomía revalida las órdenes aún no enviadas: anula las pendientes, libera sus reservas y devuelve las decisiones a confirmación. No altera misiones que ya salieron. Prioridad y estado admiten `expected_updated_at`; finalizar una misión solo es válido si ya fue aceptada o está en curso, y no declara disponible al recurso. La reactivación explícita (`resume` o `resume-simulated`) habilita el bucle automático aunque el proceso arrancara con `AGENT_AUTOSTART=false`.
- El dashboard comparte una única fuente API/SSE entre Inicio, Incidencias, Recursos y Registro. Las preguntas, notas, misiones y comunicaciones se escriben en el backend; los mocks y la simulación de rutas del navegador no inicializan datos operativos. El registro muestra estados, errores, transcripciones y run IDs de HappyRobot, pero nunca vuelca requests completos ni secretos.
