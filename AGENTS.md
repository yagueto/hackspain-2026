# Backend

- Trabaja en `apps/api` usando su `.venv` (`uv sync`). Verifica con `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy app` y `uv run pytest -q`.
- Para ejecutar también los tests SQL usa `TEST_POSTGRES_DSN` contra PostgreSQL de desarrollo. Cada test crea su propio schema temporal. El servicio de pruebas documentado usa el puerto 55432; Compose de desarrollo usa 55433 y volumen persistente.
- Persistencia: `STORAGE_BACKEND=postgres`, `DATABASE_URL` y `uv run python -m app.store.migrate --apply`. No necesita credenciales HappyRobot. Los únicos backends son `memory` y `postgres`; el adaptador Twin se eliminó y toda la lógica SQL vive en `app/store/postgres.py`.
- Configuración: entorno del proceso > `.env.local` > `.env`. Ambos dotenv y `.devin/mcp_config.local.json` deben seguir ignorados. Nunca imprimir ni versionar claves, URL privadas de webhooks o secretos.
- Las pruebas aíslan Settings de ambos dotenv y del entorno, y bloquean el transporte HTTP real. Usar ASGITransport o MockTransport; no desactivar esta protección para hacer pasar un test.
- Nunca activar comunicaciones reales durante verificaciones automáticas. Mantener `HAPPYROBOT_MODE=simulated`, `AGENT_AUTOSTART=false`; vaciar `OPENAI_API_KEY` en el proceso para pruebas completamente locales.
- Los avisos de texto salen por el workflow `send_telegram` (`HAPPYROBOT_WF_TELEGRAM`): el backend no habla con la API de Telegram ni con ningún puente. El canal SMS se eliminó por completo (`ActionKind.sms` y `/control/sms` ya no existen); `apps/simulator/simulator.py` todavía contiene una rama `kind == "sms"` inútil. El aviso queda `dispatched` hasta que llega la observación `message_outcome`; no darlo por entregado antes. Una orden cuyo `workflow` no corresponde a su `kind` debe fallar, nunca cambiar de canal.
- Solo las llamadas mueven `contact.reliability`, porque pondera la selección de medios. Un aviso de texto entregado no es evidencia de que la persona responda.
- En HappyRobot, los POST nuevos usan `webhookSchemaVersion=2` y `body={schemaVersion:2,contentType:"application/json",raw:...}` con tokens `{{$var:group_id.variable_id}}`. Confirmado que la conversión automática de strings falla: `url` y `headers[].value` exigen arrays Plate con nodos `variable`. Los `group_id` por índice (`0`) solo valen al crear en lote; para añadir nodos usar el `persistent_id` real.
- El MCP `happyrobot-workflows` (`.devin/mcp.json`) permite crear y validar workflows. `test_all` comprueba estructura y referencias, pero algunos nodos POST pueden ejecutarse; un nodo "skipped — success" no se ha ejecutado. No publicar versiones ni rellenar variables con secretos sin petición explícita.
- Publicar es **por entorno**: una versión live en `production` no la usan los runs de `development`, y el backend dispara con `HAPPYROBOT_ENVIRONMENT`. Para mover una versión hay que despublicarla antes; si no, `publish` responde "Version is already live". `fork` conserva los `persistent_id`, así que las referencias `{{$var:...}}` siguen valiendo. El aviso de "variable references could not be resolved" sobre params del trigger es un falso positivo: resuelven en ejecución.
- El nodo Webhook POST solo expone `error` como variable de salida, no `status_code` ni `response`. Y un nodo hijo solo se ejecuta si el padre tuvo éxito, así que no se puede ramificar sobre el fallo de un POST.
- No detener la API antigua con almacenamiento memory sin conservar su estado o pedir confirmación. No eliminar volúmenes de PostgreSQL.
- `apps/simulator` puede contener trabajo sin versionar del usuario; no incluirlo en commits ajenos. No hacer push sin petición explícita.
- La recepción ciudadana por Web Call usa `POST /api/v1/webhooks/happyrobot/inbound` con `X-Webhook-Secret`, `run_id`, `timestamp` ISO con zona horaria y el parte estructurado. No requiere una acción saliente. `incoming_calls` se conserva en el snapshot PostgreSQL y se difunde por SSE; cada run tiene un único aviso actualizable y los informes atrasados se ignoran.
- El usuario eligió Web Call y propuestas con aprobación, no despacho automático. Los puntos aportados requieren ambas coordenadas válidas y confirmación. También admite Nominatim para lugares públicos de prueba: exige `NOMINATIM_DEMO_ENABLED=true`, `SEED_DEMO=true` y `location.public_search_allowed=true` en el aviso, o consentimiento explícito del operador al buscar. No deducir GPS del teléfono ni consultar direcciones privadas. Un resultado geocodificado se etiqueta como aproximado; los candidatos ambiguos o centros de poblaciones no se seleccionan automáticamente.
- `Recepción llamada ciudadana` tiene la v5 `01a0ba83-54d9-7d83-8454-b78c35aa7801` publicada en `development` con autorización del usuario (sustituye a v4); añade `location_public_search_allowed` para la consulta pública opcional y propuestas con aprobación: `Web call` → `Inbound Voice Agent` → `enviar_incidencia` → POST al backend. Sin chatbot de texto ni llamadas salientes; `require_webcall_auth=true`. `INTAKE_BASE_URL` e `INTAKE_WEBHOOK_SECRET` se configuraron privadamente solo en development; el secreto coincide con `HAPPYROBOT_WEBHOOK_SECRET`. No cambiar secretos ni otras publicaciones sin autorización explícita.
- Para publicar un tool nuevo, HappyRobot exige abrir `Tool Call Result` en su interfaz. El MCP puede responder éxito al escribir `configuration.tool_call_result_ack` pero no cambia `unack`; el usuario abrió el panel y pasó realmente a `ack`. Un resultado de previsualización con campos null no prueba un fallo de una conversación: contrastar runs y recibos.
- En la sesión local el frontend 4200 apunta a la API actualizada con PostgreSQL en 8001. Un proxy de callbacks en 8010 expone solo `POST /api/v1/webhooks/happyrobot/inbound` a través de un túnel separado; no expone `/state`. Ese túnel es temporal: si se reinicia cambia la URL y hay que actualizar privadamente la variable de development. La API antigua en memoria de 8000 y su túnel no se modificaron. Las salidas siguen simuladas y el agente pausado, independientemente de los avisos entrantes reales.
- El MCP puede responder éxito a un `update` de `event_id` sin cambiar el tipo real. Releer siempre el nodo. Para reemplazar el trigger, `update_workflow_nodes action=add` con un trigger inicia un árbol nuevo y sustituye el anterior: hacerlo solo en un borrador propio, reconstruir sus hijos y usar los nuevos `persistent_id`. Un agente nuevo crea automáticamente su prompt y la vinculación `call` al trigger Web Call.
- Precaución adicional sobre `test_all`/`fix_broken_vars`: un POST no omitido puede intentar ejecutarse. En el chatbot devolvió `unsupported protocol scheme` con la base vacía. No repetir estas comprobaciones con endpoints reales bajo la suposición de que siempre son puramente estructurales.
- `app/domain/intake.py` prepara propuestas `awaiting_approval` al recibir avisos y al recuperar snapshots antiguos, incluso con el agente pausado. No reserva ni contacta antes de aprobar. Cada propuesta conserva `incoming_call_id`, fecha del aviso y destino. La aprobación exige `expected_updated_at` y `confirm_location=true`; una corrección posterior bloquea el envío de la orden antigua.
- `app/integrations/geocoding.py` usa Nominatim solo para la demo monoproceso: cola global del runtime, mínimo 1,1 segundos entre inicios, caché acotada y países limitados a España. No hace autocomplete ni polling. Guarda candidatos y errores en `incoming_calls[].resolution`, sin inventar lat/lng ni atribuir GPS. Un error del proveedor no descarta el aviso; un resultado tardío no sobrescribe una corrección.
- Los controles locales de geocodificación, ubicación y aprobación exigen `X-API-Key` (`API_KEY` del backend). `POST /control/resume-simulated` es una acción explícita aparte y rechaza modo live. Las órdenes simuladas no generan automáticamente aceptación del recurso ni significan ayuda movilizada.
